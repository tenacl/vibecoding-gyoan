이론 기초 01

AI가 답하는 원리 — 확률 기계에서 프롬프트까지

AI가 왜 그렇게 답하는지 알면, 어떻게 시켜야 하는지가 저절로 따라옵니다.

LLM은 "다음 말"을 확률로 고르는 기계

  • 110년 동안 사람들이 붙잡은 질문은 딱 하나였습니다 — "다음에 올 말은 무엇인가?"
  • 마르코프(1913, 소설을 손으로 세어 통계를 냄) → 섀넌(1948, 언어는 확률의 연쇄) → 신경망 언어모델(2003) → 트랜스포머(2017) → ChatGPT(2022) → 도구를 쥔 AI, 즉 에이전트(지금)
  • 기술은 계속 바뀌었지만 원리는 그대로입니다: 앞의 말을 보고 다음에 올 말을 확률로 예측한다

왜 같은 질문에 매번 다른 답이 나오나 — 샘플링

  • AI는 확률 1등만 고르지 않습니다. 분포에서 추첨(샘플링)하기 때문에 가끔 2등, 3등도 뽑힙니다
  • 그래서 답이 매번 달라지는 건 고장이 아니라 설계입니다 — 이걸 알면 "AI가 이상해졌나?"에서 멈추지 않게 됩니다
  • 창의성과 환각은 같은 다이얼의 양 끝입니다. 추첨 폭을 넓히면 창의적이 되고, 너무 넓히면 헛소리가 됩니다

환각(할루시네이션) — 원리상 피할 수 없는 것

  • 학습에 없는 걸 물어도 AI는 "그럴듯한 다음 단어"를 계속 만들어냅니다. 없는 함수, 없는 링크, 없는 판례를 자신 있게 지어내는 이유입니다
  • 다음 단어를 확률로 예측하는 방식의 필연적 결과라서, 프롬프트를 잘 쓴다고 사라지지 않습니다
  • ⚠️ 이 문제의 답은 이 과정 마지막에 나옵니다 — 지어내는 대신 도구로 사실을 확인하게 만드는 것(이론 03의 RAG). 지금은 "이런 문제가 있다"만 기억해두세요

그래서 프롬프트는 "확률을 좁히는 행위"입니다

막연한 요청구체적인 요청
예시"맛있는 거 주세요""매운 것 빼고, 둘이서 3만 원어치 주세요"
확률 분포평평함 — 후보가 너무 많다뾰족함 — 후보가 좁혀진다
결과그럴듯한 평균이 나온다내가 원하던 것이 나온다

PTCF — 프롬프트를 구체적으로 쓰는 틀

요소묻는 질문예시
Persona누구로서?"당신은 동네 카페의 마케터입니다"
Task무엇을?"홍보 문구를 3개 써 주세요"
Context어떤 상황에서?"손님 대부분이 출근길 30대 직장인입니다"
Format어떤 모양으로?"문구당 두 문장, 해시태그 3개씩"
  • 네 칸을 매번 다 채울 필요는 없습니다. 쓰기 전에 네 칸을 한 번 떠올리는 습관이 핵심입니다

TCREI — 프롬프트를 계속 고쳐가는 틀

요소뜻성격
Task할 일을 한 문장으로프롬프트에 넣는 재료
Context대상·배경·조건
References예시·원문·양식을 함께 준다
Evaluate나온 결과를 그냥 쓰지 않고 채점한다답을 받은 뒤 사람의 행동
Iterate어긋난 부분만 짚어 다시 시킨다
  • PTCF가 잘 "쓰는" 법이라면, TCREI는 잘 "고쳐가는" 법입니다. 한 번 쓰고 마는 프롬프트가 아니라 계속 다듬어 쓰는 프롬프트에 필요합니다
  • AI를 잘 쓰는 사람과 못 쓰는 사람은 뒤의 두 칸(E·I)에서 갈립니다. 첫 결과가 마음에 안 드는 건 정상이고, 거기서 채점하고 다시 시키느냐가 실력입니다
EXAMPLE — Evaluate → Iterate1차 결과 채점: 순서 ○, 색 ○, 대표 메뉴 ✕ (세상 카페의 평균이 나옴) → 어긋난 칸만 짚어서 다시: "대표 메뉴를 흑임자 라떼·수제 스콘·핸드드립으로 바꿔 주세요. 나머지는 그대로."

프롬프트를 구조화하는 3가지 형식

에이전트와 하네스

확률 기계에 도구·기억·순환을 붙이면 에이전트가 됩니다. 그 에이전트가 일할 환경을 짜는 것이 하네스 엔지니어링입니다.

챗봇과 에이전트 — 기준은 딱 하나

기능 개수가 아니라 "다음 단계를 누가 정하는가"로 가릅니다.

챗봇에이전트
다음 단계를 정하는 주체사람AI
비유말하는 백과사전일을 통째로 맡은 담당자
"이번 주 매출 요약해줘"방법을 알려주고 끝데이터 찾기 → 계산 → 표 만들기 → 검토를 스스로 반복
앤트로픽 공식 정의도 같은 기준입니다 — "에이전트는 LLM이 스스로 자신의 프로세스와 도구 사용을 지시하는 시스템"이고, 미리 정해진 코드 경로를 따르는 건 워크플로우입니다. 한 문장으로는: "환경 피드백을 받으며 루프 안에서 도구를 쓰는 LLM."

에이전트의 구성요소

구성요소역할없으면
추론 가능한 모델다음에 뭘 할지 판단하는 두뇌아무 결정도 못 한다
툴(도구)실제로 세상을 읽고 바꾸는 손판단만 하고 아무것도 안 바뀐다
메모리지금까지 한 일과 알게 된 것을 담는 곳매번 처음부터 다시 시작한다
(이 셋을 돌리는 루프)목표를 이룰 때까지 반복하고, 다 되면 멈춘다도구를 한 번 쓰는 챗봇에 그친다

"에이전틱하다"는 무슨 뜻일까

  • 시킨 한 가지만 하고 멈추는 게 아니라, 목표를 이루려고 AI가 스스로 할 일을 정해 여러 단계를 알아서 밟아나갈 때 "에이전틱하다(agentic)"고 말합니다
  • 비유 — 심부름을 시켰을 때 "재료가 없으면 사 오고, 그것도 없으면 대체품을 찾고, 다 되면 알려주는" 사람이 에이전틱한 사람입니다. "재료 없던데요?" 하고 그 자리에 멈추면 에이전틱하지 않은 것
  • 그런 성질을 가진 시스템이 에이전트입니다 — 명령을 받으면 스스로 계획 → 실행 → 결과 판단을 반복하며 목표까지 자율적으로 움직입니다. 바로 위 표의 "다음 단계를 AI가 정한다"가 이 뜻이고, 아래 GRAM 루프가 그 움직임을 그림으로 보여줍니다

GRAM 루프 — 에이전트가 도는 순환

  • 클로드 코드 화면에 "파일 읽는 중", "명령 실행 중"이 지나가면 지금 이 순환이 돌고 있는 것입니다 — 무서운 로그가 아니라 읽을 수 있는 진행 표시입니다
  • GRAM은 외울 표가 아니라 이름표입니다. "지금 Reason 중이구나", "방금 건 Action이네"라고 부를 수 있으면 충분합니다
  • 영어 자료를 찾을 때는 — 논문·해외 문서에서는 이 순환을 보통 agent loop라고 부르고, 학술 원전은 ReAct(Reason + Act, Yao et al. 2022)입니다

툴로 쓸 수 있는 것들

  • 파일 읽기·쓰기·수정 / 명령 실행(터미널) / 검색(파일 안 찾기, 웹 검색) / 브라우저 조작 / 외부 서비스(노션, 깃허브, DB…)
  • 외부 서비스를 붙이는 표준 규격이 MCP(Model Context Protocol)입니다 — AI에게 손·눈을 하나씩 달아주는 것이라고 생각하면 됩니다

컨텍스트 — 한국어로 "맥락"

  • 컨텍스트는 우리말로 맥락입니다. AI가 지금 우리 대화를 이해하려고 참고하는 모든 것 — 방금 던진 질문, 앞서 주고받은 대화, 읽은 파일, 붙여넣어 준 자료가 전부 컨텍스트입니다
  • AI에게는 눈치도 배경지식도 없어서 컨텍스트에 올라온 것만 압니다. 말하지 않은 사정은 모른다고 생각하는 편이 정확합니다 — 그래서 "무엇을 컨텍스트에 넣어주느냐"가 결과를 좌우합니다
  • 이 컨텍스트를 담는 그릇의 크기가 컨텍스트 윈도우, 즉 AI가 한 번에 기억할 수 있는 양입니다 (바로 아래에서 이어집니다)

  • 중요한 건 용량만이 아닙니다 — 꽉 차기 전부터 품질이 떨어집니다. 시행착오와 버린 코드가 쌓이면 확률 분포가 다시 평평해져서 답이 평균으로 흐릅니다
  • 그래서 주제가 바뀌면 새 채팅입니다. 넘쳐서가 아니라 흐려지기 전에 끊는 것입니다

이론 기초 03

RAG와 에이전틱 서치 — 환각에 대한 답

이론 01에서 던진 문제, 기억하시나요? AI는 모르는 것도 그럴듯하게 지어냅니다. 그 문제의 답이 여기 있습니다.

답은 "지어내지 말고, 찾아보게 하는 것"

  • 확률로 다음 단어를 만들어내는 대신, 실제 자료를 읽고 그걸 근거로 답하게 만듭니다
  • 이게 도구(툴)가 존재하는 근본적인 이유입니다 — 검색하고, 파일을 읽고, 코드를 실행해서 사실을 확인합니다
  • 앤트로픽이 에이전트를 "환경 피드백을 받으며 루프를 도는 LLM"이라고 정의하는 이유이기도 합니다. 여기서 환경 피드백이 곧 사실 확인입니다

RAG — 검색해서 근거를 붙인 뒤 답하기

  • RAG = Retrieval-Augmented Generation. 우리말로 하면 "검색으로 보강한 생성"입니다
  • 흐름은 단순합니다: 질문이 오면 → 관련 자료를 먼저 찾고 → 그 자료를 함께 넣어서 → 답하게 한다
  • 흔한 오해 하나 — RAG는 벡터 데이터베이스를 뜻하는 게 아닙니다. 찾아오는 방법은 무엇이든 됩니다. 클로드 코드가 내 폴더에서 파일을 검색해 읽고 답하는 것도 넓은 의미의 RAG입니다
⚠️ 가장 중요한 주의 — RAG는 환각을 없애지 않습니다.
찾아온 자료 자체가 틀렸을 수도, 맞는 자료를 잘못 읽을 수도, 자료에 없는 내용을 유추해 덧붙일 수도 있습니다. RAG가 하는 일은 환각을 제거하는 게 아니라 근거를 붙여 검증 가능하게 만드는 것입니다. "RAG를 쓰면 환각이 사라진다"는 흔한 과장이고, 오히려 결과를 확인하는 습관이 더 중요해집니다.

에이전틱 서치 — 검색을 에이전트가 스스로

  • RAG는 정해진 방식으로 한 번 찾아서 넣어줍니다. 에이전틱 서치는 에이전트가 무엇을 찾을지 스스로 판단하고, 결과를 보고 부족하면 다시 찾습니다
  • 둘은 대체 관계가 아니라 겹쳐 쓰는 관계입니다 — 에이전틱 서치는 RAG에 GRAM 루프를 얹은 것이라고 보면 됩니다
  • 기준이 낯익지 않으신가요? "다음 단계를 누가 정하는가" — 이론 02에서 챗봇과 에이전트를 가른 그 기준입니다

LLM 위키 — 찾아 쓸 지식을 아예 쌓아두기

  • RAG가 "필요할 때 찾아온다"면, 그 찾아올 대상을 미리 잘 만들어두자는 흐름이 있습니다. AI가 읽기 좋게 정리해둔 지식 창고를 LLM 위키라고 부릅니다
  • 거창한 게 아닙니다 — 마크다운 파일을 폴더로 정리한 것입니다. 표 설명, 용어 정의, 업무 절차, 과거 사고 기록 같은 것을 문서로 쌓아두고 에이전트가 참조하게 합니다
  • 이 패턴은 이미 여러 이름으로 존재해 왔습니다 — 우리가 배운 CLAUDE.md도 그중 하나입니다. 구글 클라우드가 이걸 공통 규격으로 정리한 것이 OKF(Open Knowledge Format)이고, 특별한 도구 없이 마크다운 + 폴더 구조가 전부입니다
  • 왜 중요한가 — 회사에서 진짜 필요한 지식은 대부분 내부 지식(우리 회사의 지표 정의, 이 표가 뭘 뜻하는지, 장애 대응 절차)이고, 이건 AI가 학습한 적이 없습니다. 위키에 쌓아두면 매번 설명하지 않아도 됩니다
이론 02의 장기 메모리 기억하시나요? LLM 위키는 그 장기 메모리를 개인에서 팀·조직 단위로 넓힌 것입니다. 오늘 CLAUDE.md 한 장을 쓰는 습관이, 회사에서는 팀 지식 창고를 만드는 일로 이어집니다.

컨텍스트 엔지니어링과의 관계

  • 이론 02에서 컨텍스트 엔지니어링을 "어떤 컨텍스트를 줄지 고민하는 것"이라고 했습니다
  • RAG는 그 고민을 자동화한 것입니다 — 사람이 매번 골라 넣던 자료를, 시스템이 질문에 맞춰 대신 찾아 넣어줍니다
  • 컨텍스트 윈도우에 모든 걸 넣을 수 없기 때문에 필요한 기술이기도 합니다. 다 넣으면 흐려지고, 안 넣으면 지어냅니다 — 그 사이를 푸는 게 RAG입니다
3일 과정 전체를 한 줄로 이으면 이렇게 됩니다 — 확률 기계(이론 01) → 잘 시키는 법(프롬프트) → 도구와 순환을 붙여 에이전트로(이론 02) → 사실을 확인하게 만들기(이론 03). 실습에서 만드는 모든 것이 이 사슬 위에 있습니다.

오리엔테이션 · 바이브코딩이란

코드를 직접 타이핑하지 않아도 됩니다. AI에게 한국어로 설명해서 만드는 개발 — 그게 바이브코딩입니다.

핵심 내용

  • 바이브코딩 = AI에게 "이런 걸 만들어줘"라고 말로 설명하면 AI가 코드를 대신 써주는 개발 방식. 우리는 코드를 "쓰는 사람"이 아니라 "시키고, 확인하는 사람"이 된다
  • 그래서 필요한 실력도 다르다 — 문법 암기 ❌ / 원하는 것을 정확히 설명하는 능력과 결과가 맞는지 판단하는 능력 ⭕
  • 코드를 몰라도 시작할 수 있지만, 웹이 어떤 부품으로 이루어지는지 큰 그림은 알아야 잘 시킬 수 있다 — 그래서 오늘 오전에 그 큰 그림부터 배운다
  • 3일 로드맵: Day 1 만들고 인터넷에 공개하기 → Day 2 바깥 데이터와 연결하기(API) → Day 3 데이터베이스로 진짜 저장되는 앱(노션 클론) 만들어 인터넷에 공개하기

"바이브코딩"이라는 말은 어디서 왔나

복잡한 코드를 직접 써 내려가는 일이 아닙니다. 코딩 에이전트와 대화하며, 만들고 싶은 결과물을 정확히 설명하고 이해시키는 일입니다.

  • 바이브코딩은 OpenAI 창립 멤버 안드레이 카파시(Andrej Karpathy)가 2025년 초 처음 꺼낸 말이다 — "코드를 한 줄씩 붙잡고 있는 게 아니라, 흐름(vibe)에 몸을 맡기고 AI에게 시키며 만든다"는 뜻에서 나왔다
  • 그래서 핵심은 타이핑 실력이 아니라 "무엇을, 왜 만들고 싶은지"를 말로 또렷하게 전달하는 힘이다 — 요리로 치면 내가 칼질을 하는 게 아니라, 주방장(AI)에게 원하는 요리를 정확히 주문하고 맛을 보는 사람이 되는 것
  • 주문이 뭉뚱그려지면 엉뚱한 게 나오고, 구체적으로 설명할수록 원하는 결과에 가까워진다 — 이 "설명하고 → 확인하고 → 다시 요청하는" 감각이 3일 내내 여러분이 기를 진짜 실력이다

미리 알아두면 마음 편한 것 2가지

  • AI는 확률 기계다 — 같은 질문에 매번 조금씩 다른 답이 나오는 건 고장이 아니라 원래 그렇게 설계된 것. 그리고 맥락(자료·설명)을 많이 줄수록 답이 정확해진다 — 오전에 배울 프롬프트 기술의 원리다
  • 정말 어려운 건 개발이 아니라 가입·설치·연결이다 — 계정 만들기, 키 발급에서 막히는 게 정상이다. 막히면 여러분 잘못이 아니니 바로 손 들자 (부록 「막혔을 때 응급처치」 참고)

이 교육에서 쓸 "바이브코딩 6단계" — 3일 내내 반복할 흐름

기억할 건 딱 하나입니다. 아래 6단계를 한 바퀴 돌리면 결과물 하나가 세상에 나옵니다. 그리고 이 바퀴를 3일 동안 계속 돌립니다.

이 6단계는 한 번 쓰고 버리는 순서가 아닙니다. 작은 결과물 하나를 만들 때마다 ①~⑥을 반복합니다 — 3일 동안 이 바퀴를 여러 번 돌리다 보면, 어느새 몸에 배어 여러분만의 서비스도 같은 방식으로 만들게 됩니다.

따라하기 ① — 윈도우에 Claude Code 설치

설치 순서
  1. 시작 전 확인 — Claude 유료 구독(Pro 이상) 계정으로 로그인할 수 있어야 한다. 아직 무료 계정이라면 지금 업그레이드부터 (뒤에서 로그인이 막히면 대부분 이 이유다)

환경변수 — 컴퓨터 전체가 기억하는 설정

  • 환경변수 = 특정 프로그램이 아니라 내 컴퓨터 전체에 붙여두는 메모. 어떤 프로그램이든 이 메모를 읽을 수 있다
  • 대표적인 환경변수가 Path — "명령어를 치면 어느 폴더에서 프로그램을 찾을지"의 목록. 터미널에서 claude만 쳐도 실행되는 건 Path에 설치 폴더가 등록되어 있기 때문이다
  • 그래서 claude 명령을 찾을 수 없다는 에러가 나면 = Path에 설치 폴더가 등록 안 된 것. 아래 방법으로 직접 등록하면 해결된다
  • 미리 알아두면 좋은 이유 — 내일(Day 2) 배우는 API 키도 환경변수로 보관한다. 코드에 키를 직접 적지 않는 안전한 방법이 바로 이것이다
따라하기 ② — 환경변수 창 열고 Path 등록하기
  1. 먼저 확인 — 위에서 claude --version이 잘 나왔다면 이 절차는 건너뛰어도 된다. "명령을 찾을 수 없다"는 에러가 났을 때만 따라 하자
  2. 윈도우 키를 누르고 "환경 변수"라고 검색 → "시스템 환경 변수 편집" 클릭 → 창이 뜨면 아래쪽 [환경 변수] 버튼 클릭
  3. 위쪽 "사용자 변수" 목록에서 Path를 선택하고 [편집] 클릭
  4. [새로 만들기] 클릭 → 아래 경로를 입력하고 확인을 눌러 모든 창을 닫는다
  5. 열려 있던 PowerShell을 닫았다가 새로 열고 claude --version으로 확인 — 환경변수는 새 창부터 적용된다
PATH에 추가할 경로 (Claude Code가 설치되는 위치)%USERPROFILE%\.local\bin
새 환경변수를 만들 때도 같은 창을 씁니다 — "사용자 변수"에서 [새로 만들기] → 변수 이름과 값 입력. 내일 API 키를 보관할 때 이 방법을 다시 만나게 됩니다.

터미널이란 — 마우스 대신 '말로' 시키는 창

  • 터미널(=PowerShell 같은 명령어 창) = 평소 마우스로 하던 일을 글자 명령어로 대신 시키는 프로그램. 폴더를 더블클릭해서 들어가는 대신 cd 폴더명이라고 쳐서 들어간다
  • 검은 화면에 글씨만 있어서 낯설 뿐, 어렵지 않다 — 우리가 외울 명령어는 대여섯 개면 충분하다. 나머지는 전부 Claude가 알아서 친다
  • 왜 배우나 — 가장 강력한 Claude Code가 바로 이 터미널 위에서 돌기 때문이다. 터미널을 조금 알면 클로드 코드가 무슨 일을 하는지 눈에 들어온다
[캡처/짤: 영화 매트릭스에서 트리니티가 터미널로 해킹하는 장면] — 영화 속 해커들이 검은 화면에 글자를 치는 그 창이 바로 터미널입니다. 생각보다 우리 일상과 가깝습니다.

왜 코딩 에이전트에겐 터미널이 잘 맞나

  • Claude 같은 LLM은 '언어'를 학습한 모델이다 — 그림보다 글(언어)로 주고받을 때 가장 빠르고 정확하다
  • 터미널은 모든 작업이 글자(명령어와 글자 결과)로 오간다. 그래서 마우스로 버튼을 찾아 누르는 화면 조작보다, 언어로 처리하는 터미널이 AI에겐 훨씬 효율적이고 빠른 작업 방식이다
  • 정리하면 — 사람에겐 마우스, AI에겐 터미널이 편하다. 그래서 가장 일 잘하는 AI 도구가 터미널에서 도는 것이다

로컬호스트 · 포트 · 서버 — 어렵지 않습니다

  • 서버 = 거창한 게 아니라 그냥 24시간 켜져 있는 컴퓨터다. 우리가 인스타에 접속하면, 저쪽에서 늘 켜져 있는 컴퓨터(서버)가 화면을 내려준다 — 그게 전부다
  • 로컬호스트(localhost) = 바로 내 컴퓨터 자신을 가리키는 이름(주소로는 127.0.0.1). 내가 만든 걸 남에게 공개하기 전에 나만 먼저 테스트하는 '내 컴퓨터 안 미리보기'다
  • 포트(port) = 컴퓨터라는 건물의 문 번호. 한 컴퓨터가 여러 프로그램을 동시에 돌리니, "이 프로그램은 3000번 문, 저건 5500번 문" 식으로 문을 나눠 쓴다
  • 그래서 http://localhost:3000 은 "내 컴퓨터(localhost)의 3000번 문(port)으로 들어와"라는 뜻이다. Claude가 "브라우저에서 localhost:3000 을 열어보세요"라고 하면 겁먹지 말고 그 주소를 주소창에 붙여넣으면 된다
정리 — 서버 = 늘 켜진 컴퓨터, 로컬호스트 = 내 컴퓨터, 포트 = 문 번호. 이 세 단어만 잡아두면 Day 2에서 서버를 다룰 때 훨씬 편합니다.

3개의 부품 한눈에 보기

프론트엔드 (앞단)사용자 눈에 보이는 전부 — HTML(뼈대) · CSS(모양) · JS(움직임)피드 화면

프론트엔드를 이루는 3요소 — HTML · CSS · JS

방금 만든 그 화면은 사실 세 겹으로 되어 있습니다. 집 한 채를 짓는 순서와 똑같습니다 — 골조를 세우고, 인테리어를 하고, 설비를 넣습니다.

  • HTML — 웹사이트의 뼈대·구조를 정의하는 문서 언어. "이건 제목, 이건 문단, 이건 버튼"처럼 정보에 의미를 부여해서, 검색엔진(구글·네이버)이 페이지에 무슨 내용이 있는지 알아보게 한다. 아주 예전 웹사이트들은 CSS 없이 HTML만으로 만들어졌다 — 밋밋하지만 내용은 다 담겨 있었다. → 집으로 치면 골조(뼈대)
  • CSS — 그 뼈대에 옷을 입히는 것. 색·글꼴·크기·간격·배치 같은 스타일을 담당한다. 내용은 그대로 두고 겉모습만 바꾼다. → 집으로 치면 인테리어·도색
  • JS(자바스크립트) — 웹사이트에 기능과 동작을 넣는다. 버튼을 누르면 반응하고, 화면이 움직이고, 입력을 받아 처리하는 등 사용자와 상호작용하는 부분을 맡는다. → 집으로 치면 전기·수도 같은 작동 설비
[캡처: 같은 페이지의 3단계 비교 — ① HTML만 (검은 글자만 있는 밋밋한 화면) vs ② CSS 적용 (색·배치가 입혀진 화면) vs ③ JS까지 (버튼이 눌리고 화면이 바뀌는 화면)]
요소맡은 역할집짓기에 비유하면
HTML뼈대·구조 — 무엇이 담겨 있는지, 정보에 의미 부여🏗️ 골조
CSS스타일 — 색·글꼴·배치 등 겉모습🎨 인테리어·도색
JS기능·동작 — 클릭·움직임 등 사용자와의 상호작용🔌 전기·수도 설비
EXAMPLE PROMPT (① 뼈대만 — HTML)내 자기소개 웹사이트를 HTML만으로(CSS·JS 없이) 담백하게 만들어줘. 이름, 한 줄 소개, 좋아하는 것 3가지, 연락처만 넣어줘.
EXAMPLE PROMPT (② 옷 입히기 — CSS)내용은 그대로 두고, 여기에 CSS만 더해서 더 멋지게 꾸며줘. 색·글꼴·여백을 넣어 보기 좋게.
EXAMPLE PROMPT (③ 움직임 넣기 — JS)이제 다크모드/라이트모드 전환 버튼과 그 기능을 추가해줘. 버튼을 누르면 화면 색이 바뀌게.
  • 같은 페이지를 세 번에 나눠 시켜보면, HTML→CSS→JS가 각각 무엇을 바꾸는지 눈으로 체감된다 — 뼈대만 있던 화면이 예뻐지고, 마지막엔 버튼이 실제로 작동한다

  • 반대로, 서버·DB 없이 화면에만 저장하면? 새로고침하면 지워지는 칠판과 같다 — "저장이 안 돼요"는 고장이 아니라 구조가 그렇게 되어 있는 것. 이 구조를 알면 "저장 안 돼, 고쳐줘" 대신 "데이터가 저장되게 바꿔줘"라고 짚어 말할 수 있다

프롬프트 엔지니어링 + 토큰 절약법

같은 AI라도 시키는 사람에 따라 결과가 완전히 달라집니다. 잘 시키는 법을 체화합니다.

좋은 프롬프트의 4요소 — PTCF(역할·할 일·맥락·형식)

요소스스로 묻는 질문예시
P 역할누구로서 만들게 하나?"너는 소개 페이지를 잘 만드는 웹 디자이너야"
T 할 일무엇을 만드나?"한 장짜리 소개 페이지를 만들어줘"
C 맥락대상·목적·꼭 지킬 조건은?"보는 사람은 채용 담당자 / 갈색·크림색만 / 스크롤 없이 한 화면"
F 형식어떤 모양·산출물로?"index.html 한 파일, 완성되면 브라우저로 열어줘"

여기서 '무엇이 성공인가(목표)'와 '꼭 지킬 조건(제약)'은 모두 C(맥락)에 담습니다 — 이 둘을 맥락에 넣는 것이 결과를 가장 크게 바꿉니다.

  • 모호함은 비용이다 — "예쁘게 해줘"라고 하면 AI도 찍기를 한다. "카드형 레이아웃, 여백 넉넉히, 파란 계열"처럼 구체적으로 말하면 한 번에 원하는 게 나온다
  • 토큰 = AI가 글을 읽고 쓸 때 세는 글자 조각 단위. 대화가 길어질수록 토큰이 쌓여서 느려지고, 사용량이 늘고, AI가 앞부분을 잊기 시작한다
  • 절약 습관 3가지 — ① 주제가 바뀌면 /clear로 새 대화 시작 ② 관련 있는 파일만 보여주기 ③ 한 번에 하나씩 시키기

왜 구체적이어야 하나 — "비워둔 칸은 평균으로 채워진다"

  • AI는 마음을 읽지 못한다. 내가 말하지 않은 부분은 세상의 평균으로 채운다 — "홈페이지 만들어줘"라고 하면 세상 홈페이지의 평균이 나오는 이유
  • 그래서 큰 것을 시킬 땐 첫 줄에 "단계적으로 개발할 예정이야"를 선언하고, 지금 할 일 하나만 말한다. 이 한 줄이 없으면 AI는 "완성 주문"으로 받아 한 번에 다 만들어버린다
  • 첫 결과가 마음에 안 드는 건 정상이다. 처음부터 다시 시키지 말고, 아쉬운 부분만 짚어서 다시 시킨다 — "대표 메뉴만 바꿔줘. 나머지는 그대로"

외워둘 만능 프롬프트 6개

상황이렇게 말한다
에러가 났을 때"에러 나는데 고쳐줘" + [에러 화면 스크린샷]
방금 것이 마음에 안 들 때"방금 한 거 되돌려줘" (같은 대화 안에서만 통한다)
새 대화를 시작한 직후"지금 이 프로젝트 구조랑 현재 상태 정리해줘"
다음 작업으로 넘어가기 전"지금 페이지 전체 한번 점검해줘. 깨진 거 없는지"
대화가 길어져 느려질 때/compact (요약하고 이어가기)
큰 것을 만들기 시작할 때"단계적으로 개발할 예정이야. 지금은 ○○만 만들어줘"

바이브코딩 플로우 + 깃(Git)

오후 프로젝트에서 그대로 밟을 3단계 플로우와, 내 결과물을 인터넷에 공개하는 수단(깃)을 배웁니다.

모든 프로젝트가 밟는 3단계

단계하는 일한 줄 요령
① 기획·디자인무엇을 왜 만들지 정한다"누가 보나 / 무엇을 보여주나 / 어떤 분위기인가" 세 가지만 정해도 프롬프트가 저절로 좋아진다
② 구현·디버깅만들고 고친다오전에 배운 프롬프트 기술을 여기서 쓴다 — 섹션 하나씩, 한 번에 하나만
③ 배포인터넷에 공개한다내 컴퓨터에서만 열리던 파일이 전 세계에서 열리는 URL이 된다

배포는 어떻게 이루어지나

깃(Git) — 겁먹지 않아도 되는 이유

  • 깃(Git) = 코드의 세이브 포인트. 게임처럼 "여기까지 저장"을 남겨두고, 망치면 그 지점으로 되돌린다
  • 왜 Ctrl+S로는 부족한가 — ① 어제 상태로는 못 돌아간다(Ctrl+Z의 한계) ② 컴퓨터가 고장 나면 코드가 사라진다 ③ 배포하려면 코드가 먼저 클라우드에 올라가 있어야 한다

용어뜻택배 비유

깃 vs 깃허브 — 헷갈리지 않게

이름이 비슷해서 자주 헷갈립니다. 둘은 짝꿍이지만 역할이 다릅니다 — 하나는 내 컴퓨터의 기능, 하나는 인터넷 위의 창고입니다.

깃(Git)깃허브(GitHub)
정체내 컴퓨터에서 세이브 지점을 관리하는 도구그 세이브 지점을 인터넷(클라우드)에 백업·공유하는 저장소 서비스
어디에 있나내 컴퓨터 안인터넷(웹사이트)
게임 비유게임의 저장 기능 그 자체클라우드 세이브 — 다른 기기에서도 불러오고 친구와 공유
없으면되돌리기가 안 됨내 컴퓨터가 고장 나면 코드가 사라짐
  • 즉 깃으로 세이브(커밋)하고 → 깃허브로 올린다(푸시). 이 두 단계가 한 세트다
  • 핵심 가치는 안도감 — 실험하다 망가져도 저장 지점으로 언제든 되돌릴 수 있다. 그래서 겁내지 않고 이것저것 시도할 수 있다

명령 두 개만 더 — 클론과 풀

앞의 택배 표에서 커밋(포장)·푸시(발송)는 이미 봤습니다. 반대로 가져오는 쪽 두 개만 더 알면 끝입니다.

용어뜻비유
커밋(commit)지금 상태로 세이브 지점 만들기 (앞 표 복습)물건 포장하고 송장 붙이기
푸시(push)세이브 지점을 클라우드(깃허브)에 올리기 (앞 표 복습)택배 발송
클론(clone)남의(또는 내) 저장소를 통째로 내려받기남의 상자를 통째로 복제해 내 책상에 놓기
풀(pull)클라우드의 최신 내용만 가져와 내 것에 반영바뀐 부분만 새로 배달받기

비개발자는 명령을 외울 필요가 없다

  • 위 용어들은 Claude가 하는 말을 알아듣기 위한 것이지, 내가 타이핑하려고 외우는 게 아니다
  • 실제로는 말로 시키면 Claude가 대신 처리한다. 아래처럼 부탁하면 된다
EXAMPLE PROMPT (깃 시작하기)이 폴더에 깃을 초기화해줘. 앞으로 여기서 저장 지점을 만들 수 있게.
EXAMPLE PROMPT (세이브 = 커밋)지금까지 만든 걸 커밋해줘. 커밋 메시지는 지금 상태에 맞게 적당히 지어줘.
EXAMPLE PROMPT (세이브 목록 보기)지금까지의 커밋 이력을 보기 쉽게 보여줘.
EXAMPLE PROMPT (되돌리기)방금 것 말고, 그 이전 커밋 상태로 되돌려줘.
커밋은 자주 하는 게 좋습니다 — 뭔가 제대로 작동하는 지점마다 세이브하세요. 그래야 나중에 망가졌을 때 가장 가까운 멀쩡한 지점으로 돌아올 수 있습니다. "잘 되던 순간"을 그때그때 붙잡아 두는 것이 핵심입니다. 그리고 깃허브를 쓰려면 GitHub 계정이 필요합니다 — 준비물 안내를 참고해 미리 가입해 두세요(무료).

에러를 만나면 이 순서로 — F12 → Console → 캡처

디버깅 3원칙 — 3일 내내 쓰게 된다

원칙이렇게 한다왜

③ 한 번에 하나버그 하나 고치고 확인, 그다음 하나동시에 고치면 뭐가 문제였는지 알 수 없다

여러 번 고쳤는데 점점 더 꼬인다면, 고치는 것보다 새로 만드는 게 빠를 때가 있습니다. 새 폴더를 만들고 지금까지 배운 걸로 다시 시키세요 — 두 번째는 훨씬 빠릅니다. 망가진 프로젝트를 붙들고 있는 것보다 훨씬 나은 선택이고, 실패가 아닙니다.

같은 "게임 만들어줘"라도 — 지시가 구체적일수록 결과가 좋아진다

이번 실습은 사과게임으로 "구체적으로 지시하는 연습"을 합니다. 완성이 목적이 아니라, 규칙을 얼마나 또박또박 설명하느냐에 따라 결과가 어떻게 달라지는지 몸으로 느끼는 게 목적입니다.

  • 그냥 "게임 만들어줘"라고 하면 AI는 빈칸을 자기 마음대로 채웁니다 — 내가 상상한 게임과 전혀 다른 게 나오기 쉽습니다
  • 반대로 규칙·화면·조작법을 구체적으로 풀어주면, AI는 내 머릿속에 훨씬 가깝게 만들어줍니다. 이게 바이브코딩에서 가장 중요한 기술입니다
  • 그래서 오늘은 내가 원하는 것을 말로 정확히 풀어내는 연습을 사과게임으로 합니다

사과게임이란 — 이 규칙을 그대로 AI에게 설명하게 됩니다

  • 화면에 1~9 숫자가 적힌 사과들이 직사각형 격자(줄과 칸)로 빽빽하게 놓여 있습니다
  • 플레이어는 마우스로 드래그해서 사각형 범위를 지정해 그 안의 사과들을 한꺼번에 선택합니다
  • 선택한 사과 숫자의 합이 정확히 10이면 그 사과들이 사라지고 점수가 오릅니다 (10이 아니면 아무 일도 없음)
  • 제한 시간(예: 2분) 안에 최대한 많은 사과를 없애는 것이 목표입니다
  • 실제로 어떤 게임인지 먼저 직접 해보면 규칙 설명이 훨씬 쉬워집니다 → gamesaien.com 사과게임(Fruit Box)
먼저 진짜 게임을 3분만 해보세요. 직접 플레이해 본 게임은 규칙을 설명하기가 훨씬 쉽습니다. "드래그하면 어떻게 되는지", "합이 10일 때 무슨 일이 일어나는지"를 눈으로 확인한 뒤 AI에게 설명하면 결과물의 완성도가 확 올라갑니다.
실습 — 사과게임 만들기
  1. 먼저 진짜 사과게임을 잠깐 해보며 규칙을 눈에 익힌다
  2. 바로 "만들어줘"가 아니라, 아래처럼 "계획부터 세워줘"라고 시킨다 — AI가 세운 계획을 읽어보면 내 설명에서 빠진 부분이 보인다
  3. 계획이 마음에 들면 "이 계획대로 만들어줘"라고 이어서 시킨다

  5. 버그를 만나면 아래 버그 신고 템플릿으로 신고한다

EXAMPLE PROMPT (최종 산출물 형태 — 실행 방법 지정)완성되면 index.html 파일 하나로 만들어줘. 따로 서버를 켜지 않아도, 그 파일을 더블클릭하면 브라우저에서 바로 열려서 플레이할 수 있게 해줘.

DAY 210:10–10:40이론

API란 무엇인가

오늘 하루 종일 쓰게 될 단 하나의 개념 — "정해진 형식으로 요청하면, 데이터가 온다."

핵심 내용

  • API = Application Programming Interface의 약자. "응용 프로그램끼리 대화하는 접속 창구"라는 뜻으로, 다른 회사의 데이터·기능을 정해진 형식으로 가져다 쓰는 통로다
  • 흐름은 항상 같다: 요청("이 주소로 서울 미세먼지 주세요") → 응답("여기 있습니다"). 응답은 주로 JSON(JavaScript Object Notation의 약자)이라는 형식 — 중괄호 { }로 정리된 데이터 꾸러미인데, 읽고 해석하는 건 AI가 해주니 겁먹지 않아도 된다
  • API 키 = "나는 요청할 자격이 있어요"를 증명하는 열쇠. 발급받은 사람 명의로 사용량이 기록된다
  • 무료 API는 어디서 찾나 — 공공데이터포털(data.go.kr, 정부가 공개한 데이터), Google Cloud 콘솔(구글 서비스들)

⚠️ 키는 비밀번호다 — 오늘 가장 중요한 안전 수칙

  • 어제 깃허브에 올리는 법을 배웠기 때문에 오늘이 가장 위험한 날이다 — 키가 적힌 코드를 그대로 올리면, 남이 내 키로 마구 요청해서 요금 폭탄을 맞을 수 있다
  • 안전 수칙 ① — Claude에게 "API 키가 코드에 노출되지 않게 해줘"라고 요청하기
  • 안전 수칙 ② — 깃허브에 올리기 전, 키가 든 파일이 포함됐는지 반드시 확인하기
  • "그런데 오늘 실습은 키를 페이지 코드에 넣던데요?" — 맞다. 오늘은 연습용 무료 키라서 코드에 넣고 배우되, 그 코드를 깃허브에 올리지 않는 것이 오늘의 규칙이다. 실제 서비스라면 키를 서버 쪽에 숨긴다 — 그게 백엔드가 필요한 또 하나의 이유다

  • 그래서 키가 전혀 필요 없는 API로 "API 붙이는 성공"을 먼저 한 번 맛봅니다. 성공 경험을 손에 쥐고 나면, 뒤에 나오는 준비 단계들이 훨씬 만만해집니다
  • 핵심은 준비물이 아니라 흐름입니다 — 정해진 주소로 요청하면 데이터가 응답으로 오고, 그걸 화면에 뿌린다. 이 한 바퀴를 이번 실습에서 몸으로 겪어 둡니다

picsum.photos — 키가 필요 없는 API

  • picsum.photos는 주소 하나만 부르면 랜덤 사진을 돌려주는 무료 이미지 API입니다. 회원가입도, API 키도 없습니다 — 주소가 곧 요청입니다
  • 예를 들어 https://picsum.photos/300 이라고 요청하면 가로·세로 300픽셀짜리 랜덤 이미지 한 장이 옵니다. 주소 끝의 숫자가 이미지 크기이고, 부를 때마다 다른 사진이 나옵니다
  • 브라우저 주소창에 https://picsum.photos/300을 그대로 쳐 보세요. 매번 새 사진이 뜨는 게 보이면, 그게 바로 API가 응답하는 순간입니다 — 어렵게 느껴지던 "API 호출"이 사실 이렇게 간단한 일이라는 걸 눈으로 확인하는 단계입니다
주소 뒤에 조금씩 붙여 보면 API에 "옵션을 얹는" 감이 잡힙니다 — /300/200은 가로 300·세로 200, /300?grayscale은 흑백, /300?blur는 흐릿하게. 이렇게 같은 API에 요청을 조금씩 바꿔 보는 것이 내일 진짜 API를 다룰 때도 그대로 쓰이는 습관입니다.

실습 — 가상 미술관 사이트 만들기

  • 이 API로 사진 전시회처럼 보이는 웹사이트를 만듭니다. 랜덤 이미지 30장 정도를 격자(그리드)로 정렬해, 진짜 온라인 갤러리처럼 보이게 하는 게 목표입니다
  • 지난 세션들처럼 계획부터 세우게 하는(plan-first) 프롬프트로 시작합니다 — 바로 코드를 뽑게 하지 않고, AI가 먼저 만들 순서를 말하게 한 뒤 진행하면 결과가 훨씬 깔끔합니다
실습
  1. 새 폴더를 하나 만들고, 아래 계획 먼저 프롬프트를 넣어 미술관 사이트의 뼈대를 생성합니다
  2. AI가 내놓은 계획을 한 번 읽고 "좋아, 그대로 만들어줘"로 진행합니다 — 계획이 마음에 안 들면 이 단계에서 고쳐 달라고 하면 됩니다
  3. 완성된 페이지를 브라우저로 엽니다. 랜덤 사진 30장이 격자로 뜨면 1차 성공 — 새로고침 할 때마다 사진이 바뀌는 것도 확인해 보세요
  4. 아래 개선 프롬프트로 전시회다운 디테일을 얹어 완성도를 높입니다

공공 API + 데이터 시각화 — 주식 시세 대시보드

데이터베이스 입문 — 내 데이터를 어디에 저장하나

지금까지 만든 앱들은 데이터가 내 브라우저 안에만 갇혀 있었습니다. 여러 사람이 함께 쓰는 진짜 서비스로 넘어가려면 데이터베이스가 필요합니다. 다음 세션의 노션 클론을 위한 발판입니다.

먼저, 오늘 만들 앱을 상상해 봅시다

  • 잠시 뒤 우리가 직접 만들 localStorage 할 일 앱을 떠올려 봅시다. 새로고침해도 내용이 남습니다 — 브라우저가 내 컴퓨터 한구석에 적어두기 때문입니다
  • 그런데 여기엔 결정적인 한계가 있습니다 — 그 데이터는 "내 브라우저에만" 저장됩니다. 다른 기기(내 폰), 다른 사람(친구)에게는 절대 보이지 않습니다. 심지어 같은 컴퓨터라도 다른 브라우저를 켜면 텅 비어 있습니다
  • 즉 localStorage는 혼자 쓰는 개인 메모장일 뿐입니다. "친구와 같이 쓰는 할 일 목록", "어느 기기서든 이어지는 노트" 같은 걸 만들려면 데이터를 모두가 접근하는 한곳에 모아야 합니다. 그곳이 바로 데이터베이스입니다

데이터베이스란 무엇인가

데이터베이스(DB)는 두 가지가 합쳐진 것입니다 — 데이터를 쌓아두는 공간과, 그 데이터를 안전하게 넣고 꺼내주는 관리 시스템.

비유하자면 거대한 도서관입니다. 책을 꽂아두는 서가(공간)만 있으면 금방 아수라장이 됩니다. 어디에 무엇을 두고, 누가 빌려갔고, 어떻게 빨리 찾아줄지 관리하는 사서(관리 시스템)가 있어야 도서관이 됩니다. DB도 마찬가지로 저장 공간 + 똑똑한 사서가 한 세트입니다.
  • 사서가 있으니 수백만 건이 쌓여도 원하는 데이터를 순식간에 찾고, 여러 사람이 동시에 요청해도 뒤엉키지 않게 정리해 줍니다
  • 우리는 이 사서에게 "이런 걸 넣어줘 / 저런 걸 꺼내줘"라고 부탁만 하면 됩니다. 창고를 직접 뒤질 필요가 없습니다

두 가지 종류 맛보기 — 관계형 vs 문서형

데이터베이스에도 성격이 다른 종류가 있습니다. 깊은 내용은 심화에서 다루고, 지금은 이런 게 있다 정도만 알면 충분합니다.

생김새엑셀 표처럼 행·열이 딱 정해진 칸자유로운 서류 뭉치 — 칸이 유연함
비유📊 줄이 딱 맞는 회계 장부🗂️ 내용이 제각각인 서류철

  • 다음 세션에서 쓸 Supabase는 관계형(엑셀 표 방식)입니다. 우리에게 익숙한 표 형태라 이해하기 쉽습니다

데이터로 하는 일은 딱 4가지 — CRUD

메모 앱이든 노션이든 쇼핑몰이든, 데이터로 하는 일은 결국 이 네 가지의 조합입니다. 앞 글자를 따 CRUD(크러드)라고 부릅니다.

동작뜻메모 앱에서라면
Create (만들기)새 데이터를 넣는다새 메모를 쓴다
Read (읽기)저장된 데이터를 꺼내 본다메모 목록을 펼쳐 본다
Update (수정)기존 데이터를 고친다메모 내용을 고친다
Delete (삭제)데이터를 지운다메모를 버린다
  • 이 네 단어만 알면 어떤 앱이든 "무엇을 만들고, 읽고, 고치고, 지우는지"로 쪼개어 AI에게 시킬 수 있습니다. 노션 클론도 결국 페이지에 대한 CRUD일 뿐입니다
실습 — 저장을 눈으로 확인하고, 그 한계까지 만나기
  1. 새 폴더에서 Claude에게 아래 계획 먼저(plan-first) 프롬프트를 줍니다. 계획이 나오면 한 번 읽어보고 실행합니다
  2. 완성되면 할 일을 3~4개 추가해 봅니다 (Create). 목록이 화면에 뜹니다 (Read)
  3. 이제 핵심 — 브라우저를 새로고침(F5) 합니다. 놀랍게도 방금 쓴 할 일이 그대로 남아 있습니다. localStorage가 데이터를 저장한 것입니다. 데이터가 "저장된다"는 걸 눈으로 확인하는 순간입니다
  4. 한계 확인 — 같은 페이지 주소를 다른 브라우저(예: 크롬에서 만들었다면 엣지)나 휴대폰에서 열어봅니다. 텅 비어 있습니다. "이 데이터는 내 브라우저에만 있었구나"를 몸으로 확인합니다. 이게 바로 다음 세션에서 진짜 DB가 필요한 이유입니다
EXAMPLE PROMPT (계획 먼저 — plan-first)바로 만들지 말고 계획부터 보여줘. 브라우저의 localStorage를 써서 새로고침해도 목록이 남는 간단한 할 일 앱을 HTML 파일 하나로 만들 거야. 기능은 딱 네 가지 — 할 일 추가, 목록 보기, 완료 체크(수정), 삭제. 계획이 마음에 들면 그때 만들어줘.
지금은 localStorage라 데이터가 내 브라우저 안에만 남습니다. "왜 폰에서는 안 보이지?"라는 이 답답함이, 다음 세션에서 진짜 데이터베이스로 넘어가는 출발점입니다.

그래서 다음 세션에서는

  • 오늘 배운 개념(데이터베이스 · 관계형 · CRUD)을 그대로 써서, 이번엔 진짜 데이터베이스인 Supabase에 저장되는 노션 클론을 만듭니다
  • 그러면 localStorage의 한계가 사라집니다 — 어느 기기에서든, 여러 사람이 함께 같은 데이터를 보고 고칠 수 있게 됩니다. "내 브라우저에만"에서 "모두의 저장소로" 넘어가는 순간입니다

이 장을 마치면

  • 데이터베이스가 "저장 공간 + 관리 시스템(사서)"이라는 걸 도서관에 비유해 설명할 수 있다
  • 관계형과 문서형의 차이를 한 문장으로 말할 수 있고, Supabase가 관계형이라는 걸 안다
  • CRUD 네 가지가 무엇인지 말할 수 있다
  • localStorage로 저장을 눈으로 확인하고, "내 브라우저에만" 남는 한계까지 직접 만나봤다

  • 많은 사람이 "이런 거 나도 만들어보고 싶다"고 생각하는 대표적인 앱이라, 오늘의 따라하기 소재로 딱 좋습니다
  • 진짜 노션은 기능이 아주 많지만, 우리는 그 뼈대 하나만 그대로 따라 만듭니다 — 페이지를 만들고 저장하는 부분이요

오늘 만드는 것

  • 노션처럼 페이지를 만들고(Create)·목록으로 보고(Read)·수정하고(Update)·삭제(Delete) 되는 간단한 앱. 이 네 가지를 앞글자만 따서 CRUD(크러드)라고 부릅니다 — 데이터 앱의 기본 4동작이에요
  • 이 네 가지가 되면, 사실상 "내 데이터를 저장하는 앱"의 뼈대는 다 갖춘 셈입니다. 메모장·가계부·일기·독서기록 — 전부 같은 CRUD 위에 얹혀 있어요
  • 회원가입·소셜 로그인(구글로 로그인 같은 것)은 오늘은 하지 않습니다. 그건 심화로 미루고, 오늘은 CRUD 하나에만 집중합니다. 욕심내면 하루로 안 끝나요

지금 상태 — localhost는 나만 볼 수 있다

  • 노션 클론을 실행하면 주소창에 localhost:3000 같은 주소가 떴을 겁니다. 여기서 localhost = 바로 이 컴퓨터라는 뜻입니다 — 내 컴퓨터에서만 열리는 주소이고, 옆 사람에게 이 주소를 보내도 열리지 않습니다
  • Day 1에서 프로필 페이지를 GitHub Pages로 공개했던 것처럼, 이번엔 이 앱을 인터넷에 올릴 차례입니다. 그런데 이번 앱은 DB가 붙어 있어서 방법이 조금 다릅니다 — 왜 다른지부터 봅니다

정적 배포 vs 동적 배포 — 왜 GitHub Pages로는 안 되나

Day 1의 프로필 페이지와 오늘의 노션 클론은 종류가 다른 웹입니다. 이 차이를 알면 "왜 새 서비스를 배워야 하나"가 한 번에 이해됩니다.

  • GitHub Pages는 완성된 파일을 그대로 보여주기만 합니다. 뒤에서 일해줄 서버가 없어서, "글을 저장하면 DB에 넣어라" 같은 움직이는 일을 시킬 데가 없습니다
  • 그래서 동적 앱은 서버를 대신 굴려주는 배포 서비스가 필요합니다. 오늘 쓰는 것이 Vercel입니다

Vercel — GitHub만 연결하면 알아서 올려주는 서비스

  • Vercel(버셀, vercel.com) = 내 GitHub 저장소를 연결하면 자동으로 빌드·배포해주는 서비스. 동적 앱에 필요한 서버까지 알아서 준비해 줍니다
  • 무료로 시작할 수 있고, 개인 프로젝트나 오늘 만든 노션 클론 정도는 무료 범위로 충분합니다
  • 한 번 연결해 두면, 이후에는 GitHub에 새로 올리기(푸시)만 하면 Vercel이 알아서 다시 배포합니다 — Day 1에서 파일을 다시 올리면 사이트가 갱신되던 것과 같은 느낌입니다
Day 1에서 배운 커밋(포장)·푸시(발송)가 여기서 그대로 쓰입니다. Vercel은 그 "발송된 택배(GitHub 저장소)"를 받아 자동으로 진열대에 올려주는 배달 대행이라고 생각하면 됩니다.

③ 환경변수 — 키는 코드에 넣지 않는다

Day 1에서 "API 키는 환경변수로 보관한다"고 배웠습니다. Vercel 배포에서 그 개념을 실제로 씁니다. 노션 클론은 DB(Supabase)에 접속하려면 비밀 키가 필요한데, 이 키를 코드 안에 적어 두면 안 됩니다.

  • 환경변수 = 프로그램이 실행될 때 읽어가는 바깥에 붙여둔 설정 메모. 키를 코드에 직접 쓰지 않고, 이 메모에 적어두면 코드는 "그 메모를 읽어" 사용합니다
  • 왜 이렇게 하나 — 키가 코드에 박혀 있으면, 코드를 GitHub에 올리는 순간 키까지 온 세상에 공개됩니다. 남이 내 DB를 마음대로 열 수 있게 되는 셈입니다
  • 그래서 키는 Vercel의 환경변수 칸(Environment Variables)에 따로 등록합니다 — 코드에는 "키를 여기서 읽어와" 하는 표시만 남고, 진짜 값은 Vercel이 안전하게 보관합니다

혼자 해보기 — 배포된 내 노션 클론에 나만의 기능 하나(예: 페이지에 날짜 표시, 검색창)를 Claude에게 시켜 붙이고, 다시 커밋·푸시하면 Vercel이 자동으로 새로 배포한다. 스스로 붙인 첫 기능이다.

보안 — 키가 GitHub에 올라가면 벌어지는 일

설치 상세 가이드 — 도구 4종 한 번에

준비 체크리스트에서 이름만 봤던 도구들을 실제로 설치하는 화면 단위 절차입니다. 순서대로 하나씩 따라오면 됩니다. 막히면 그 도구 항목의 버전 확인 명령부터 다시 해보세요 — 결과가 나오면 설치 성공입니다.

시작 전에 — "터미널"이 뭔가요?

  • 터미널은 컴퓨터에 글자로 명령을 내리는 검은 창입니다. 아래 설치들이 잘 됐는지 확인할 때 씁니다
  • 윈도우: 시작 버튼 → terminal 또는 PowerShell 검색 → 열기
  • 맥: command+space → terminal 입력 → 열기
  • 이 창에 아래 버전 확인 명령을 그대로 치고 Enter를 누르면 됩니다
버전 확인 명령을 쳤을 때 숫자(예: v22.11.0)가 나오면 설치 성공, "명령을 찾을 수 없습니다 / not recognized"가 나오면 설치가 안 됐거나 터미널을 껐다 다시 켜야 합니다. 설치 후에는 항상 터미널을 새로 여세요.

① Node.js — 웹과 클로드 코드의 기본 엔진

클로드 코드를 설치하려면 Node.js가 먼저 있어야 합니다. 웹 프로젝트를 돌리는 데도 쓰입니다.

  1. 다운로드: https://nodejs.org 접속 → 큰 버튼 두 개 중 "LTS"라고 적힌 쪽을 클릭 (LTS = 안정 버전, 초보자 권장). [캡처: nodejs.org 다운로드 화면 — LTS 버튼 강조]
  2. 설치 실행: 내려받은 설치 파일을 더블클릭 → Next(다음)만 계속 눌러 진행 → 마지막에 Install/Finish
  3. 설치 중 "Tools for Native Modules" 같은 추가 체크박스가 나와도 그냥 기본값으로 두고 Next 하면 됩니다
  4. 버전 확인: 터미널을 새로 열고 아래 두 명령을 차례로 입력
    명령확인 내용정상 예시
    node -vNode.js 버전v22.11.0
    npm -v함께 깔리는 npm 버전10.9.0
    [캡처: 터미널에서 node -v 와 npm -v 실행 결과]
npm은 Node.js를 설치하면 자동으로 함께 깔립니다. 따로 설치할 필요 없습니다.

② Git — 코드 저장·배포 도구

Day 1 오후에 내 웹페이지를 인터넷에 공개(배포)할 때 씁니다. 미리 깔아두세요.

  1. 다운로드: https://git-scm.com/downloads 접속 → 본인 운영체제(Windows / macOS) 클릭 → 다운로드 시작. [캡처: git-scm 다운로드 페이지]
  2. 설치 실행 (윈도우): 설치 파일 더블클릭 → 옵션 화면이 여러 번 나오지만 전부 기본값 그대로 Next → Install
  3. 설치 실행 (맥): 보통 이미 깔려 있는 경우가 많습니다. 아래 버전 확인이 되면 추가 설치가 필요 없습니다
  4. 버전 확인: 터미널을 새로 열고 git --version 입력 → git version 2.47.0 처럼 나오면 성공. [캡처: git --version 실행 결과]
윈도우 설치 중 "기본 에디터 선택" 화면이 나와 당황할 수 있는데, 그냥 기본값으로 두고 Next 하면 수업에 지장 없습니다.

③ Python — 설치 중 체크박스 하나가 핵심

일부 프로젝트·도구가 Python을 사용합니다. 설치 자체보다 체크박스 하나가 더 중요합니다.

  1. 다운로드: https://www.python.org/downloads/ 접속 → 노란 "Download Python 3.x" 버튼 클릭. [캡처: python.org 다운로드 화면]
  2. 설치 실행 — 가장 중요: 설치 파일을 더블클릭하면 첫 화면 아래쪽에 "Add Python to PATH" 체크박스가 있습니다. 반드시 먼저 체크하세요. 이걸 놓치면 터미널에서 python 명령을 못 찾습니다. [캡처: "Add Python to PATH" 체크박스에 체크한 화면]
  3. 체크를 확인했으면 "Install Now" 클릭 → 완료까지 대기 → Close
  4. 버전 확인: 터미널을 새로 열고 python --version 입력 → Python 3.13.1 처럼 나오면 성공
    • 맥에서 안 되면 python3 --version 으로 시도해 보세요
"Add Python to PATH"를 깜빡했다면? 당황하지 말고 설치 파일을 다시 실행 → "Modify(수정)" 선택 → PATH 옵션을 켜고 다시 진행하면 됩니다. 처음부터 다시 깔 필요 없습니다.

④ Claude Code(클로드 코드) — 이 수업의 주력 도구

위 ①~③이 끝나야 설치할 수 있습니다. 특히 Node.js가 먼저 깔려 있어야 합니다. 유료 Claude 구독(Pro 이상)도 필요합니다.

(a) 설치 전 준비

  • Node.js 설치 확인: 터미널에서 node -v가 버전을 출력하는지 다시 확인
  • Claude 계정: 유료 구독 상태로 claude.com에 로그인되는지 확인 (무료 계정으로는 사용 불가 — 준비 체크리스트 참고)

(b) 설치 — 이 수업은 Day 1 「개발환경 구성」 세션에서 클로드 코드를 PowerShell 네이티브 설치 방식으로 깝니다(설치 경로 %USERPROFILE%\.local\bin). 여기서는 설치가 끝난 뒤의 확인과 환경변수 정리만 다룹니다.

[확인 필요: 클로드 코드 공식 설치 명령/다운로드 — 최신 형태를 공식 문서 docs.claude.com의 Claude Code 설치 페이지에서 확정하세요. 네이티브 설치(PowerShell)와 npm 설치(@anthropic-ai/claude-code) 두 방식이 있을 수 있습니다.]
  • 설치가 끝나면 버전 확인: claude --version 입력 → 버전 번호가 나오면 성공
  • 실행: 프로젝트 폴더에서 claude 라고만 치면 클로드 코드가 시작됩니다

(c) 윈도우 환경변수(PATH) 추가 — claude 명령을 "찾을 수 없다"고 나올 때만 하면 됩니다

설치는 됐는데 터미널이 claude 명령을 못 찾는 경우, 컴퓨터에게 "그 프로그램이 어디 있는지" 알려주는 작업이 PATH 추가입니다.

  1. 시작 버튼 → 환경 변수 검색 → "시스템 환경 변수 편집" 클릭 (또는 제어판 → 시스템 및 보안 → 시스템 → 고급 시스템 설정)
  2. 열린 "시스템 속성" 창 아래쪽 "환경 변수(N)..." 버튼 클릭
  3. 아래 "사용자 변수"에서 "Path"를 찾아 클릭 → "편집(E)..." 버튼 클릭. [캡처: 환경 변수 편집 창 — Path 선택 상태]
  4. "새로 만들기(N)" 클릭 → 클로드 코드가 설치된 폴더 경로 %USERPROFILE%\.local\bin 를 붙여넣기
  5. "확인"을 모든 창에서 차례로 눌러 닫기 → 터미널을 완전히 껐다가 새로 열고 claude --version 재시도
환경변수는 초보자가 가장 어려워하는 단계입니다. 혼자 씨름하지 말고 이 화면을 캡처해서 강사에게 보여주거나, 클로드에게 "claude 명령을 못 찾는다는데 윈도우 PATH를 어떻게 확인하면 되냐"고 물어보세요. 대부분 5분이면 해결됩니다.

이 장을 마치면

  • node -v · npm -v가 버전을 출력한다
  • git --version이 버전을 출력한다
  • python --version이 버전을 출력한다 (설치 때 "Add Python to PATH" 체크함)
  • claude --version이 버전을 출력하고, claude로 클로드 코드가 실행된다

앱처럼 쓰는 반응형 웹 — 내 폰에 설치되는 웹앱

Day 1에 만든 프로필 페이지가 오늘 내 폰 홈 화면의 앱이 됩니다.

핵심 내용

  • 앱처럼 쓰는 웹(설치되는 웹앱) = 홈 화면에 설치되고 전체화면으로 열리는 웹입니다. 아이콘으로 실행하면 겉보기엔 일반 앱과 거의 같습니다
  • 필요한 것은 딱 두 가지 — manifest(앱 이름·아이콘 정보가 담긴 파일) + 서비스워커(설치를 가능하게 해주는 스크립트). 둘 다 Claude가 만들어준다
  • 한 가지 조건이 있는데, 이렇게 설치되는 웹은 https 주소에서만 설치됩니다. 다행히 GitHub Pages 주소는 자동으로 https라서 — 어제 배포한 그대로면 조건이 이미 갖춰져 있습니다

앱스토어 앱과 뭐가 다른가

설치되는 웹앱 (오늘)앱스토어 앱
배포심사·등록 없이 즉시스토어 심사 필요 (며칠~몇 주)
설치브라우저에서 "홈 화면에 추가"스토어에서 다운로드
수정 반영재배포하면 즉시업데이트 심사 후
폰 기능일부 제한 (알림 등)전부 사용 가능
  • 오늘 우리의 핵심은 "설치되는 경험"이므로 이 방식이 딱 맞다
실습 — 프로필 페이지를 앱으로
  1. Day 1 프로필 프로젝트 폴더를 열고, 아래 프롬프트를 보낸다
  2. 바뀐 파일들을 깃허브에 다시 올린다 (Day 1 배포와 같은 방법)
  3. 폰 브라우저로 내 주소를 열고 — 안드로이드(크롬): 메뉴(⋮) → 홈 화면에 추가 / 아이폰: 꼭 사파리로 열어서 공유 버튼 → 홈 화면에 추가 (아이폰용 크롬에는 이 메뉴가 없으니 헤매지 말자)
  4. 홈 화면의 내 앱 아이콘을 눌러 전체화면으로 열리면 성공

MS Clarity — 실사용자는 내 서비스를 어떻게 쓰는가

"만들었다"에서 끝나지 않고, 사람들이 실제로 어떻게 쓰는지 보고 고치는 것 — 그게 서비스 운영입니다.

핵심 내용

  • MS Clarity = 마이크로소프트가 무료로 제공하는 사용자 행동 분석 도구. 내 사이트에 온 사람들이 어디를 누르고, 어디까지 읽고, 어디서 나가는지 보여준다
  • 오늘 시연은 미리 설치해 데이터가 쌓여 있는 사이트로 본다 — Clarity는 설치 후 데이터가 대시보드에 뜨기까지 수십 분~수 시간이 걸려서, 여러분 사이트의 데이터는 내일 확인하게 된다

무엇을 볼 수 있고, 보고 나서 무엇을 하나

기능보여주는 것보고 나서 할 일
히트맵많이 클릭된 곳일수록 빨갛게아무도 안 누르는 버튼은 없앤다
세션 녹화방문자가 쓰는 모습을 영상처럼 재생다들 이탈하는 지점을 고친다
분노의 클릭안 되는 버튼을 연타한 흔적고장 났거나 헷갈리는 버튼을 찾아 고친다
실습 — 내 사이트에 설치
  1. clarity.microsoft.com 접속 → 마이크로소프트 또는 구글 계정으로 가입
  2. 새 프로젝트 만들기 → 프로젝트 이름과 내 배포 주소를 입력하고 만들기 → 설정 → 설치로 들어가면 "직접 설치" 탭에 추적 코드가 보인다 — 통째로 복사한다
  3. Claude에게 "이 스크립트를 내 페이지의 head에 넣어줘"라고 하고 복사한 코드를 붙여넣는다
  4. 깃허브에 다시 올려 재배포하면 설치 끝 — 데이터는 오늘 저녁~내일 대시보드에서 확인

이 장을 마치면

  • 추적 코드가 들어간 내 사이트가 다시 배포되어 있다
  • 내일 대시보드에서 무엇을 볼지(히트맵·세션 녹화) 알고 있다
