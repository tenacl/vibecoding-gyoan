이론 기초 01

AI가 답하는 원리 — 확률 기계에서 프롬프트까지

AI가 왜 그렇게 답하는지 알면, 어떻게 시켜야 하는지가 저절로 따라옵니다.

LLM은 "다음 말"을 확률로 고르는 기계

  • 110년 동안 사람들이 붙잡은 질문은 딱 하나였습니다 — "다음에 올 말은 무엇인가?"
  • 마르코프(1913, 소설을 손으로 세어 통계를 냄) → 섀넌(1948, 언어는 확률의 연쇄) → 신경망 언어모델(2003) → 트랜스포머(2017) → ChatGPT(2022) → 도구를 쥔 AI, 즉 에이전트(지금)
  • 기술은 계속 바뀌었지만 원리는 그대로입니다: 앞의 말을 보고 다음에 올 말을 확률로 예측한다

왜 같은 질문에 매번 다른 답이 나오나 — 샘플링

  • AI는 확률 1등만 고르지 않습니다. 분포에서 추첨(샘플링)하기 때문에 가끔 2등, 3등도 뽑힙니다
  • 그래서 답이 매번 달라지는 건 고장이 아니라 설계입니다 — 이걸 알면 "AI가 이상해졌나?"에서 멈추지 않게 됩니다
  • 창의성과 환각은 같은 다이얼의 양 끝입니다. 추첨 폭을 넓히면 창의적이 되고, 너무 넓히면 헛소리가 됩니다

환각(할루시네이션) — 원리상 피할 수 없는 것

  • 학습에 없는 걸 물어도 AI는 "그럴듯한 다음 단어"를 계속 만들어냅니다. 없는 함수, 없는 링크, 없는 판례를 자신 있게 지어내는 이유입니다
  • 다음 단어를 확률로 예측하는 방식의 필연적 결과라서, 프롬프트를 잘 쓴다고 사라지지 않습니다
  • ⚠️ 이 문제의 답은 이 과정 마지막에 나옵니다 — 지어내는 대신 도구로 사실을 확인하게 만드는 것(이론 03의 RAG). 지금은 "이런 문제가 있다"만 기억해두세요

그래서 프롬프트는 "확률을 좁히는 행위"입니다

막연한 요청구체적인 요청
예시"맛있는 거 주세요""매운 것 빼고, 둘이서 3만 원어치 주세요"
확률 분포평평함 — 후보가 너무 많다뾰족함 — 후보가 좁혀진다
결과그럴듯한 평균이 나온다내가 원하던 것이 나온다

PTCF — 프롬프트를 구체적으로 쓰는 틀

요소묻는 질문예시
Persona누구로서?"당신은 동네 카페의 마케터입니다"
Task무엇을?"홍보 문구를 3개 써 주세요"
Context어떤 상황에서?"손님 대부분이 출근길 30대 직장인입니다"
Format어떤 모양으로?"문구당 두 문장, 해시태그 3개씩"
  • 네 칸을 매번 다 채울 필요는 없습니다. 쓰기 전에 네 칸을 한 번 떠올리는 습관이 핵심입니다

TCREI — 프롬프트를 계속 고쳐가는 틀

요소뜻성격
Task할 일을 한 문장으로프롬프트에 넣는 재료
Context대상·배경·조건
References예시·원문·양식을 함께 준다
Evaluate나온 결과를 그냥 쓰지 않고 채점한다답을 받은 뒤 사람의 행동
Iterate어긋난 부분만 짚어 다시 시킨다
  • PTCF가 잘 "쓰는" 법이라면, TCREI는 잘 "고쳐가는" 법입니다. 한 번 쓰고 마는 프롬프트가 아니라 계속 다듬어 쓰는 프롬프트에 필요합니다
  • AI를 잘 쓰는 사람과 못 쓰는 사람은 뒤의 두 칸(E·I)에서 갈립니다. 첫 결과가 마음에 안 드는 건 정상이고, 거기서 채점하고 다시 시키느냐가 실력입니다
EXAMPLE — Evaluate → Iterate1차 결과 채점: 순서 ○, 색 ○, 대표 메뉴 ✕ (세상 카페의 평균이 나옴) → 어긋난 칸만 짚어서 다시: "대표 메뉴를 흑임자 라떼·수제 스콘·핸드드립으로 바꿔 주세요. 나머지는 그대로."

프롬프트를 구조화하는 3가지 형식

형식 없는 긴 글은 AI에게 "다 한 줄"로 보입니다. 구역을 나눠주면 조건이 서로 섞이지 않습니다.

GRAM 루프 — 에이전트가 도는 순환

  • 클로드 코드 화면에 "파일 읽는 중", "명령 실행 중"이 지나가면 지금 이 순환이 돌고 있는 것입니다 — 무서운 로그가 아니라 읽을 수 있는 진행 표시입니다
  • GRAM은 외울 표가 아니라 이름표입니다. "지금 Reason 중이구나", "방금 건 Action이네"라고 부를 수 있으면 충분합니다
  • 영어 자료를 찾을 때는 — 논문·해외 문서에서는 이 순환을 보통 agent loop라고 부르고, 학술 원전은 ReAct(Reason + Act, Yao et al. 2022)입니다

툴로 쓸 수 있는 것들

  • 파일 읽기·쓰기·수정 / 명령 실행(터미널) / 검색(파일 안 찾기, 웹 검색) / 브라우저 조작 / 외부 서비스(노션, 깃허브, DB…)
  • 외부 서비스를 붙이는 표준 규격이 MCP(Model Context Protocol)입니다 — AI에게 손·눈을 하나씩 달아주는 것이라고 생각하면 됩니다

컨텍스트 윈도우 — 왜 새 주제는 새 채팅인가

  • AI가 한 번에 기억할 수 있는 양입니다. 무한하지 않습니다
  • 중요한 건 용량만이 아닙니다 — 꽉 차기 전부터 품질이 떨어집니다. 시행착오와 버린 코드가 쌓이면 확률 분포가 다시 평평해져서 답이 평균으로 흐릅니다
  • 그래서 주제가 바뀌면 새 채팅입니다. 넘쳐서가 아니라 흐려지기 전에 끊는 것입니다

RAG와 에이전틱 서치 — 환각에 대한 답

이론 01에서 던진 문제, 기억하시나요? AI는 모르는 것도 그럴듯하게 지어냅니다. 그 문제의 답이 여기 있습니다.

답은 "지어내지 말고, 찾아보게 하는 것"

  • 확률로 다음 단어를 만들어내는 대신, 실제 자료를 읽고 그걸 근거로 답하게 만듭니다
  • 이게 도구(툴)가 존재하는 근본적인 이유입니다 — 검색하고, 파일을 읽고, 코드를 실행해서 사실을 확인합니다
  • 앤트로픽이 에이전트를 "환경 피드백을 받으며 루프를 도는 LLM"이라고 정의하는 이유이기도 합니다. 여기서 환경 피드백이 곧 사실 확인입니다

RAG — 검색해서 근거를 붙인 뒤 답하기

  • RAG = Retrieval-Augmented Generation. 우리말로 하면 "검색으로 보강한 생성"입니다
  • 흐름은 단순합니다: 질문이 오면 → 관련 자료를 먼저 찾고 → 그 자료를 함께 넣어서 → 답하게 한다
  • 흔한 오해 하나 — RAG는 벡터 데이터베이스를 뜻하는 게 아닙니다. 찾아오는 방법은 무엇이든 됩니다. 클로드 코드가 내 폴더에서 파일을 검색해 읽고 답하는 것도 넓은 의미의 RAG입니다
⚠️ 가장 중요한 주의 — RAG는 환각을 없애지 않습니다.
찾아온 자료 자체가 틀렸을 수도, 맞는 자료를 잘못 읽을 수도, 자료에 없는 내용을 유추해 덧붙일 수도 있습니다. RAG가 하는 일은 환각을 제거하는 게 아니라 근거를 붙여 검증 가능하게 만드는 것입니다. "RAG를 쓰면 환각이 사라진다"는 흔한 과장이고, 오히려 결과를 확인하는 습관이 더 중요해집니다.

에이전틱 서치 — 검색을 에이전트가 스스로

  • RAG는 정해진 방식으로 한 번 찾아서 넣어줍니다. 에이전틱 서치는 에이전트가 무엇을 찾을지 스스로 판단하고, 결과를 보고 부족하면 다시 찾습니다
  • 둘은 대체 관계가 아니라 겹쳐 쓰는 관계입니다 — 에이전틱 서치는 RAG에 GRAM 루프를 얹은 것이라고 보면 됩니다
  • 기준이 낯익지 않으신가요? "다음 단계를 누가 정하는가" — 이론 02에서 챗봇과 에이전트를 가른 그 기준입니다

컨텍스트 엔지니어링과의 관계

  • 이론 02에서 컨텍스트 엔지니어링을 "어떤 컨텍스트를 줄지 고민하는 것"이라고 했습니다
  • RAG는 그 고민을 자동화한 것입니다 — 사람이 매번 골라 넣던 자료를, 시스템이 질문에 맞춰 대신 찾아 넣어줍니다
  • 컨텍스트 윈도우에 모든 걸 넣을 수 없기 때문에 필요한 기술이기도 합니다. 다 넣으면 흐려지고, 안 넣으면 지어냅니다 — 그 사이를 푸는 게 RAG입니다
3일 과정 전체를 한 줄로 이으면 이렇게 됩니다 — 확률 기계(이론 01) → 잘 시키는 법(프롬프트) → 도구와 순환을 붙여 에이전트로(이론 02) → 사실을 확인하게 만들기(이론 03). 실습에서 만드는 모든 것이 이 사슬 위에 있습니다.

오리엔테이션 · 바이브코딩이란

코드를 직접 타이핑하지 않아도 됩니다. AI에게 한국어로 설명해서 만드는 개발 — 그게 바이브코딩입니다.

핵심 내용

  • 바이브코딩 = AI에게 "이런 걸 만들어줘"라고 말로 설명하면 AI가 코드를 대신 써주는 개발 방식. 우리는 코드를 "쓰는 사람"이 아니라 "시키고, 확인하는 사람"이 된다
  • 그래서 필요한 실력도 다르다 — 문법 암기 ❌ / 원하는 것을 정확히 설명하는 능력과 결과가 맞는지 판단하는 능력 ⭕
  • 코드를 몰라도 시작할 수 있지만, 웹이 어떤 부품으로 이루어지는지 큰 그림은 알아야 잘 시킬 수 있다 — 그래서 오늘 오전에 그 큰 그림부터 배운다
  • 3일 로드맵: Day 1 만들고 인터넷에 공개하기 → Day 2 바깥 데이터와 연결하기(API) → Day 3 운영 배우기 + 내 서비스 만들어 발표하기

미리 알아두면 마음 편한 것 2가지

  • AI는 확률 기계다 — 같은 질문에 매번 조금씩 다른 답이 나오는 건 고장이 아니라 원래 그렇게 설계된 것. 그리고 맥락(자료·설명)을 많이 줄수록 답이 정확해진다 — 오전에 배울 프롬프트 기술의 원리다
  • 정말 어려운 건 개발이 아니라 가입·설치·연결이다 — 계정 만들기, 키 발급에서 막히는 게 정상이다. 막히면 여러분 잘못이 아니니 바로 손 들자 (부록 「막혔을 때 응급처치」 참고)

Claude를 쓸 수 있는 3가지 방법을 알아보고, 수업용 환경을 세팅해 첫 결과물을 띄웁니다.

Claude를 쓰는 3가지 창구

환경모습어울리는 일
데스크톱 앱메신저처럼 대화하는 창질문, 아이디어 정리, 문서 작업

  • 수업에서는 한 가지 환경으로 전원 통일해서 진행한다 — 지금부터 다 같이 설치한다

따라하기 ① — 윈도우에 Claude Code 설치

설치 순서 (5분)
  1. 시작 전 확인 — Claude 유료 구독(Pro 이상) 계정으로 로그인할 수 있어야 한다. 아직 무료 계정이라면 지금 업그레이드부터 (뒤에서 로그인이 막히면 대부분 이 이유다)
  2. PowerShell 열기 — 키보드에서 윈도우 키를 누르고 "powershell"이라고 친 뒤 Enter (관리자 권한 필요 없음)
  3. 아래 명령어를 복사해서 PowerShell 창에 붙여넣고(마우스 우클릭 = 붙여넣기) Enter — 설치가 자동으로 진행된다
  4. 설치가 끝나면 PowerShell 창을 닫았다가 새로 연다 (새 창이어야 설치를 인식한다)
  5. 새 창에서 claude --version을 쳐본다 — 버전 번호가 나오면 설치 성공
  6. claude를 치면 첫 실행 — 브라우저가 열리면서 로그인 화면이 뜬다. Claude 계정으로 로그인하고, 화면에 코드가 나오면 복사해서 터미널에 붙여넣는다. "Login successful"이 뜨면 끝. 참고로 클로드 코드는 유료 구독(Pro 이상) 계정이어야 쓸 수 있다 — 로그인이 됐는데도 안 된다면 대부분 이 이유다
POWERSHELL — 설치 명령어 (한 줄 그대로 복사)irm https://claude.ai/install.ps1 | iex
  • 참고 — Node.js가 이미 설치된 컴퓨터라면 npm install -g @anthropic-ai/claude-code로도 설치할 수 있다 (Node.js 22 이상). 오늘은 위의 한 줄 방식으로 통일한다
  • VS Code 확장은 VS Code 왼쪽의 확장(Extensions) 아이콘 → "Claude Code" 검색 → 설치

환경변수 — 컴퓨터 전체가 기억하는 설정

  • 환경변수 = 특정 프로그램이 아니라 내 컴퓨터 전체에 붙여두는 메모. 어떤 프로그램이든 이 메모를 읽을 수 있다
  • 대표적인 환경변수가 Path — "명령어를 치면 어느 폴더에서 프로그램을 찾을지"의 목록. 터미널에서 claude만 쳐도 실행되는 건 Path에 설치 폴더가 등록되어 있기 때문이다
  • 그래서 claude 명령을 찾을 수 없다는 에러가 나면 = Path에 설치 폴더가 등록 안 된 것. 아래 방법으로 직접 등록하면 해결된다
  • 미리 알아두면 좋은 이유 — 내일(Day 2) 배우는 API 키도 환경변수로 보관한다. 코드에 키를 직접 적지 않는 안전한 방법이 바로 이것이다
따라하기 ② — 환경변수 창 열고 Path 등록하기
  1. 먼저 확인 — 위에서 claude --version이 잘 나왔다면 이 절차는 건너뛰어도 된다. "명령을 찾을 수 없다"는 에러가 났을 때만 따라 하자
  2. 윈도우 키를 누르고 "환경 변수"라고 검색 → "시스템 환경 변수 편집" 클릭 → 창이 뜨면 아래쪽 [환경 변수] 버튼 클릭
  3. 위쪽 "사용자 변수" 목록에서 Path를 선택하고 [편집] 클릭
  4. [새로 만들기] 클릭 → 아래 경로를 입력하고 확인을 눌러 모든 창을 닫는다
  5. 열려 있던 PowerShell을 닫았다가 새로 열고 claude --version으로 확인 — 환경변수는 새 창부터 적용된다
PATH에 추가할 경로 (Claude Code가 설치되는 위치)%USERPROFILE%\.local\bin
새 환경변수를 만들 때도 같은 창을 씁니다 — "사용자 변수"에서 [새로 만들기] → 변수 이름과 값 입력. 내일 API 키를 보관할 때 이 방법을 다시 만나게 됩니다.

웹의 구조 — 프론트엔드 / 백엔드 / 데이터베이스

웹 서비스는 딱 3개의 부품으로 이루어집니다. 이 큰 그림만 잡으면 AI에게 훨씬 잘 시킬 수 있습니다.

3개의 부품 한눈에 보기

부품하는 일인스타그램으로 치면
프론트엔드 (앞단)사용자 눈에 보이는 전부 — HTML(뼈대) · CSS(모양) · JS(움직임)피드 화면
백엔드 (뒷단)화면 뒤에서 일하는 서버 — 로그인 확인, 주문 접수처럼 화면에 못 맡기는 일좋아요를 접수하는 서버
데이터베이스 (DB)껐다 켜도 남아야 하는 데이터의 창고 — 회원 목록, 주문 내역그 기록이 저장되는 곳
  • 이름의 뜻 — HTML(HyperText Markup Language, 문서의 구조를 적는 언어) · CSS(Cascading Style Sheets, 색·모양을 정하는 규칙) · JS(JavaScript, 움직임을 만드는 프로그래밍 언어) · DB(Database, 데이터베이스)
  • 방금 만든 페이지가 바로 프론트엔드다 — 오늘 만드는 것들은 전부 프론트엔드만으로 완성된다
  • 백엔드와 DB가 "필요해지는 순간"은 Day 2에 직접 만나게 된다

"저장"은 어떻게 이루어지나 — 왕복 4단계

  • 쇼핑몰에서 "주문하기"를 누르면: ① 화면이 서버에 요청 → ② 서버가 DB에 기록 → ③ DB가 결과를 돌려줌 → ④ 서버가 화면에 "완료" 알림. 웹 서비스 대부분이 이 왕복의 반복이다
  • 반대로, 서버·DB 없이 화면에만 저장하면? 새로고침하면 지워지는 칠판과 같다 — "저장이 안 돼요"는 고장이 아니라 구조가 그렇게 되어 있는 것. 이 구조를 알면 "저장 안 돼, 고쳐줘" 대신 "데이터가 저장되게 바꿔줘"라고 짚어 말할 수 있다

코드를 읽는 눈 — 딱 4단어

목표는 코드를 쓰는 게 아니라, Claude의 계획·보고를 알아듣는 것. 이 4단어면 충분하다.

단어쉬운 뜻예
변수값에 붙인 이름표price = 3000 — '가격'을 부르는 방법
조건문"만약 ~라면"점수가 100이면 → "축하" 표시 (if)
반복문"각각에 대해"상품 100개를 하나씩 화면에 그리기 (for)
함수이름 붙인 작업 묶음"점수계산()" — 자주 하는 일을 한 단어로
  • 읽는 눈이 생기면 지시가 달라진다 — "그 부분 좀 고쳐줘" 대신 "조건문의 기준 금액을 5만 원으로 바꿔줘"
실습 — 내 페이지 해부하기
  1. 브라우저에서 F12 키(노트북은 Fn+F12)를 눌러 개발자도구를 연다. 위쪽의 Elements(요소) 탭에서 내가 쓴 문장을 찾아보자 — 그게 바로 HTML이다. 오른쪽 Styles 영역에 보이는 것이 CSS다
  2. Claude에게 물어본다: "이 페이지에서 프론트엔드는 어디까지야? 백엔드가 필요해지는 기능 3개를 제안해줘"

  4. Claude가 "이 페이지에는 그런 코드가 없다"고 하면 당황하지 말자 — 첫 페이지는 단순해서 그럴 수 있다. "그럼 간단한 예시를 하나 추가해서 보여줘"라고 이어서 시키면 된다

프롬프트 엔지니어링 + 토큰 절약법

같은 AI라도 시키는 사람에 따라 결과가 완전히 달라집니다. 잘 시키는 법을 체화합니다.

좋은 프롬프트의 4요소

요소스스로 묻는 질문예시
맥락나는 누구고 왜 필요한가?"나는 카페 창업을 준비하는 사람이야"
목표무엇이 되면 성공인가?"3초 안에 '따뜻한 동네 카페' 인상을 주는 페이지"
제약꼭 지켜야 할 조건은?"한 파일, 스크롤 없이 한 화면, 갈색·크림색만"
예시참고할 모습·구성은?"상단 로고, 중앙 한 줄 소개, 하단 버튼"
  • 모호함은 비용이다 — "예쁘게 해줘"라고 하면 AI도 찍기를 한다. "카드형 레이아웃, 여백 넉넉히, 파란 계열"처럼 구체적으로 말하면 한 번에 원하는 게 나온다
  • 토큰 = AI가 글을 읽고 쓸 때 세는 글자 조각 단위. 대화가 길어질수록 토큰이 쌓여서 느려지고, 사용량이 늘고, AI가 앞부분을 잊기 시작한다
  • 절약 습관 3가지 — ① 주제가 바뀌면 /clear로 새 대화 시작 ② 관련 있는 파일만 보여주기 ③ 한 번에 하나씩 시키기

왜 구체적이어야 하나 — "비워둔 칸은 평균으로 채워진다"

  • AI는 마음을 읽지 못한다. 내가 말하지 않은 부분은 세상의 평균으로 채운다 — "홈페이지 만들어줘"라고 하면 세상 홈페이지의 평균이 나오는 이유
  • 그래서 큰 것을 시킬 땐 첫 줄에 "단계적으로 개발할 예정이야"를 선언하고, 지금 할 일 하나만 말한다. 이 한 줄이 없으면 AI는 "완성 주문"으로 받아 한 번에 다 만들어버린다
  • 첫 결과가 마음에 안 드는 건 정상이다. 처음부터 다시 시키지 말고, 아쉬운 부분만 짚어서 다시 시킨다 — "대표 메뉴만 바꿔줘. 나머지는 그대로"

외워둘 만능 프롬프트 6개

상황이렇게 말한다
에러가 났을 때"에러 나는데 고쳐줘" + [에러 화면 스크린샷]
방금 것이 마음에 안 들 때"방금 한 거 되돌려줘" (같은 대화 안에서만 통한다)
새 대화를 시작한 직후"지금 이 프로젝트 구조랑 현재 상태 정리해줘"
다음 작업으로 넘어가기 전"지금 페이지 전체 한번 점검해줘. 깨진 거 없는지"
대화가 길어져 느려질 때/compact (요약하고 이어가기)
큰 것을 만들기 시작할 때"단계적으로 개발할 예정이야. 지금은 ○○만 만들어줘"
실습 — 나쁜 프롬프트 vs 좋은 프롬프트
  1. 1차: "자기소개 페이지 예쁘게 만들어줘"로 요청해 결과를 본다
  2. 2차: 아래처럼 맥락·목표·제약·예시를 갖춘 프롬프트로 다시 요청한다
  3. 두 결과를 나란히 놓고 비교한다 — 어떤 요소가 결과를 가장 크게 바꿨는지 찾아보자

단계하는 일한 줄 요령

깃(Git) — 겁먹지 않아도 되는 이유

  • 왜 Ctrl+S로는 부족한가 — ① 어제 상태로는 못 돌아간다(Ctrl+Z의 한계) ② 컴퓨터가 고장 나면 코드가 사라진다 ③ 배포하려면 코드가 먼저 클라우드에 올라가 있어야 한다

용어 4개 — 택배로 기억하기

용어뜻택배 비유
저장소내 프로젝트가 사는 방 (GitHub 위)택배 상자

푸시클라우드(GitHub)에 올리기발송

  • Claude가 "커밋하겠습니다"라고 말하면 = "포장해서 저장 지점을 만들겠다"는 뜻이다

API란 무엇인가

오늘 하루 종일 쓰게 될 단 하나의 개념 — "정해진 형식으로 요청하면, 데이터가 온다."

핵심 내용

  • API = Application Programming Interface의 약자. "응용 프로그램끼리 대화하는 접속 창구"라는 뜻으로, 다른 회사의 데이터·기능을 정해진 형식으로 가져다 쓰는 통로다
  • 흐름은 항상 같다: 요청("이 주소로 서울 미세먼지 주세요") → 응답("여기 있습니다"). 응답은 주로 JSON(JavaScript Object Notation의 약자)이라는 형식 — 중괄호 { }로 정리된 데이터 꾸러미인데, 읽고 해석하는 건 AI가 해주니 겁먹지 않아도 된다
  • API 키 = "나는 요청할 자격이 있어요"를 증명하는 열쇠. 발급받은 사람 명의로 사용량이 기록된다
  • 무료 API는 어디서 찾나 — 공공데이터포털(data.go.kr, 정부가 공개한 데이터), Google Cloud 콘솔(구글 서비스들)

⚠️ 키는 비밀번호다 — 오늘 가장 중요한 안전 수칙

  • 어제 깃허브에 올리는 법을 배웠기 때문에 오늘이 가장 위험한 날이다 — 키가 적힌 코드를 그대로 올리면, 남이 내 키로 마구 요청해서 요금 폭탄을 맞을 수 있다
  • 안전 수칙 ① — Claude에게 "API 키가 코드에 노출되지 않게 해줘"라고 요청하기
  • 안전 수칙 ② — 깃허브에 올리기 전, 키가 든 파일이 포함됐는지 반드시 확인하기
  • "그런데 오늘 실습은 키를 페이지 코드에 넣던데요?" — 맞다. 오늘은 연습용 무료 키라서 코드에 넣고 배우되, 그 코드를 깃허브에 올리지 않는 것이 오늘의 규칙이다. 실제 서비스라면 키를 서버 쪽에 숨긴다 — 그게 백엔드가 필요한 또 하나의 이유다

  • Google Cloud 콘솔 (구글 API 키 발급)console.cloud.google.com

  • PWA(Progressive Web App의 약자, "점진적 웹 앱") = 홈 화면에 설치되고 전체화면으로 열리는 웹앱. 아이콘으로 실행하면 겉보기엔 일반 앱과 거의 같다
  • 필요한 것은 딱 두 가지 — manifest(앱 이름·아이콘 정보가 담긴 파일) + 서비스워커(설치를 가능하게 해주는 스크립트). 둘 다 Claude가 만들어준다
  • 한 가지 조건이 있는데, PWA는 https 주소에서만 설치된다. 다행히 GitHub Pages 주소는 자동으로 https라서 — 어제 배포한 그대로면 조건이 이미 갖춰져 있다

막혔을 때 응급처치

시간을 잡아먹는 건 개발이 아니라 가입·설치·연결입니다. 막히는 것은 여러분 잘못이 아닙니다 — 아래 순서대로 해보세요.

무조건 먼저 해볼 3가지

  • ① 에러 메시지(또는 화면)를 그대로 복사/캡처해서 Claude에게 "이 에러 해결해줘"
  • ② 새 대화를 열고 다시 시켜보기 — 대화가 길어지면 판단이 흐려진다
  • ③ 프로그램(터미널·VS Code)을 완전히 껐다가 다시 켜기 — "바꿨는데 반영이 안 됨"의 절반은 재시작으로 풀린다
막힘의 3대 원인은 순서대로 — ① 계정(가입·로그인·키가 잘못됨) ② 연결(서비스끼리 이어지지 않음) ③ 재시작 안 함(바꾼 게 반영 안 됨). 이 순서로 점검하면 대부분 잡힙니다.
